- **c-suiteの補間候補**：run03と保存済みCのStage 2パラメータを混ぜる操作であり、追加学習ではない。

継続学習では、Stage 2のLoRA行列A/Bを更新する。例えばrun03から候補Xを学習した場合、最終重みは `W_pretrain + ΔW_stage1 + ΔW_stage2_X`。`ΔW_stage2_run03`と`ΔW_stage2_X`を両方足すことはしない。候補XのStage 2自体がrun03から更新された重みを含んでいる。

#### Stage 1・Stage 2の由来

公式配布物は2段階で学習するコードの枠組みであり、今回使うStage 1・Stage 2の学習済みadapterが公式から配布されたわけではない。run01で、公開Qwen3-4B-Baseに対してTuluの指示追従データ2,000件でStage 1をSFTし、その後GSM8KでStage 2をSFTした。教材・件数等は実行用設定で選択した。[配布原本との比較記録](research/20261013_math_sft_plan.md)

以降は**run01で学習したStage 1を共通利用し、数学用Stage 2を変更**している。Stage 2はadapterの役割・保存単位を指す。後続ではDPOやオンライン報酬学習でも更新するため、「Stage 2＝必ずSFT」という意味ではない。

#### adapterと統合の意味

adapterはLoRAの小さな追加パラメータ。対象層の本体重みを \(W\) とすると、LoRAによる実効重みは \(W+\Delta W\)、差分は \(\Delta W=(\alpha/r)BA\) で表せる。保存・更新するのは低rankの行列A/Bであり、巨大な差分行列を直接学習するわけではない。

最終モデルの重みは、対象層ごとに概念的には次の形になる（量子化・浮動小数点の丸めを省略）。

```text
W_final = W_pretrain + ΔW_stage1 + ΔW_stage2
                      └─固定─┘   └─実験で変更─┘
固定する土台 = W_pretrain + ΔW_stage1
ΔW_stage2 = (alpha / rank) × B2 × A2
```

`merge_and_unload()`はadapterの差分を本体に足し込み、別のadapter部品を持たない形へ統合する処理。学習ではない。`model = ...`が複数回出てきても、毎回独立したBaseモデルを新規初期化する意味ではない。

```python
# 処理の概略。既存モデルへ学習済み差分を順番に統合する。
model = AutoModelForCausalLM.from_pretrained(base_model, ...)
model = PeftModel.from_pretrained(model, stage1_adapter).merge_and_unload()
# Base＋Stage 1を保存し、全実験の共通の土台にする。
model = PeftModel.from_pretrained(model, stage2_adapter).merge_and_unload()
# 候補Stage 2を含む推論用モデルを保存する。
```

実装は[worker.merge()](remote/math_training/worker.py)。土台が保存済みならそれを読み込み、Stage 2の統合だけを行う。一方、学習用の`load_train_model()`では土台を4bitで読み、Stage 2を学習可能なLoRAとして取り付けたまま更新する。

SHAはファイルの内容から計算するSHA-256ハッシュ値で、取得したadapterや保存済みモデルが記録と同じ内容か確認するために使う。モデルの精度・品質を判定する数値ではない。

「継続更新」は既存のA/Bを初期値として更新する意味。例えばrun06は `(A2, B2)_run04 → (A2, B2)_run06` であり、最終モデルは `W_pretrain + ΔW_stage1 + ΔW_stage2_run06`。ここにrun04のStage 2をもう一度足したり、新規Stage 3を重ねたりしない。

また、SFT→onlineで引き継ぐのはadapterの重み。別プロセスで読み直してオンライン用optimizerを新しく作る。同一条件の途中再開では、その条件のcheckpointからoptimizer・乱数状態等も復元する。実験条件間で重みを引き継ぐことと、中断再開は区別する。

```text
共通の土台：Qwen3-4B-Base＋run01 Stage 1（以降固定）
├─ 新規Stage 2 → run01
├─ 新規Stage 2 → run02
├─ 新規Stage 2 → run03
│   ├─ run05（実行結果未確認）
│   ├─ 自己生成RFT／DPO／DFTの各学習条件
│   ├─ 公開GSM／LIMOの各学習条件
│   ├─ c-suiteの形式比較・主学習
│   ├─ accuracy-suiteのcontinue SFT ─┐
│   └─ accuracy-suiteの直接online   │
├─ 新規Stage 2 → run04 → run06      │
└─ 新規Stage 2 → accuracy-suiteのfresh SFT
                                  │
       continue／freshのSFT候補から条件を満たす最良候補を選ぶ
                                  ↓
                       best_sftからのonline
```

初期値の分岐は[worker.load_train_model()](remote/math_training/worker.py)、SFT条件とonline開始点の選択は[AccuracySuite.sft()／online()](remote/math_training/accuracy_suite.py)、オンライン用optimizerの作成は[online_worker.train()](remote/math_training/online_worker.py)を参照。

### 2. 自己生成回答によるRFT・DPO・DFT（10月16〜18日の記録）

最初の比較では512問×4回答を生成し、183組・2 epochsで学習。正解数はb0 253/400、RFT 255/400、DPO 253/400。RFTの反復は121→196問へ増えた。

#### 前段の課題 → 文献・データ → 実行

run04/run06がrun03を下回ったため、既存解説の増量・選別とは別に、**モデル自身の正解と誤答を学習信号にできるか**を検証する方針へ移った。[10/15の計画](research/20261015_automatic_reasoning_training_plan.md)では、最良run03から独立した枝を作り、同じ自動生成データでRFTとDPOを比較することを優先した。

- **参考文献と採用点**：[DPO](https://arxiv.org/abs/2305.18290)から正負応答の相対尤度を学ぶ方式、[Self-Explore](https://arxiv.org/html/2404.10346v2)から数学の最終回答の正誤による自動ペアの発想を採用。[RFTの研究](https://arxiv.org/abs/2308.01825)は正解生成経路を再学習する候補として同日の関連ノートに記録されている。Self-Exploreの途中段階を探索する方式は実行していない。
- **使用データ**：run03の既存PRM/GSM問題から機械的に抽出し、run03自身が生成した応答を自動採点。外部論文の教材をそのまま使用したわけではない。最初は512問×4生成から183組。後続suiteでは183／787／1,566例・ペアの条件を比較した。
- **pilotから7候補へ**：pilotではRFTの正答数増加が小さく反復が増え、DPOも正答数が変わらなかった。後続では学習率・例の範囲・lossを比較した。[DFT](https://arxiv.org/html/2508.05629v3)は以前の計画で挙げた教師トークンの重み付け候補で、後続suiteに追加された。ただし7候補の各ハイパーパラメータの選定理由すべてを説明する計画記録は確認できていない。
- **結果から次へ**：7候補でも正答率の明確な改善がなく、自己生成をさらに増やす優先度を下げ、教師となる解説の供給元を公開GSM/LIMOへ変える比較に進んだ。

### 5. 現在取り組んでいる実験：正解率優先のaccuracy-suite（10月20日実装）

Cの提出結果を受け、正解率を主指標に戻した。反復半減を採用条件から外し、推論環境差を主要因とする方針も採らない。起動オプションは **`--accuracy-suite`**。学習・評価の固定時間上限は設けず、有限の教師トークン量・オンラインラウンド数で終了する。

**教師あり学習の6条件**：PRM:GSM=3:1、回答のみのNLL、実効batch16。教材数が異なる条件も同じ教師トークン予算で比較する。

| 条件 | 出発点 | 教材数 | 学習率 | 終了形式 |
| --- | --- | ---: | ---: | --- |
| 主比較1 | run03の継続 | 6,000 | 1e-5 | F11 |
| 主比較2 | 共通Stage 1＋新規Stage 2 | 6,000 | 1e-5 | F11 |
| 主比較3 | run03の継続 | 12,000 | 1e-5 | F11 |
| 主比較4 | 共通Stage 1＋新規Stage 2 | 12,000 | 1e-5 | F11 |
| 低学習率対照 | run03の継続 | 6,000 | 5e-6 | F11 |
| 終了形式対照 | run03の継続 | 6,000 | 5e-6 | F10 |

F11はGSMの既存計算注記除去・構造化最終値のboxed化＋旧chat終端、F10は同じ本文＋直接EOS。終了形式対照は問題と更新グループを一致させる。PRMの解説本文は書き換えない。

- **教材と量**：公式PRMの完成解説と公式GSMを使用。旧run03の6,000問すべての問題対応を確認済み。PRMの段階評価ラベルは使わない。初期指定は最大400万教師トークン/枝、1例最大3回。CPU前処理で得た共通予算は3,530,379教師トークン。途中地点も評価する。
- **生成能力の診断**：探索用devの128問で8回答ずつ生成し、単一greedy、sampled pass@1、pass@8を区別する。診断結果から個別の訓練問題を選び直さない。
- **オンライン正誤報酬学習**：run03と、条件を満たす最良SFT候補があればその候補の最大2枝。1ラウンド4問×8生成→自動採点→1更新、初期値128ラウンド/枝。現在のモデルで毎回生成し直すon-policy REINFORCE。報酬は最終答えの正誤だけで、短さや通常終了への加点はない。全正解・全不正解のグループは勾配ゼロなので、実更新数を別記する。
- **採用判定**：旧dev400で+2ポイント以上の最良1候補を凍結し、新規確認400問、続いて新規最終400問で比較する。それぞれ正答率差のpaired bootstrap区間の下限が0を上回ることを要求する。反復率も報告するが半減は要求しない。提出スコアは別途確認する。
- **確認済み**：実装、CPUテスト、実データ前処理、既知6,000問の対応、分割漏洩防止、オンライン勾配・保存再読込等。
- **未確認**：新suiteのGPU起動・進捗、CUDA通し実行、実時間、各候補の成績、新しい提出スコア。結果が届くまではrun03超えとは扱わない。

#### 前段の課題 → 現在の仮説と文献の位置づけ

最新Cがrun03を超えなかったため、[10/20の実装記録](remote/math_training/README.md)では、最高値を出したPRM/GSM構成を起点に、次の未分離要因を比較する設計にした。

| 前段に残った課題 | 今回比較すること | 根拠の位置づけ |
| --- | --- | --- |
| run03→04では問題数と更新量が同時に増えた | 6,000／12,000件を同じ教師トークン予算で比較 | 過去実験の交絡を減らす独自設計 |
| 新規Stage 2と既存重みへの継続で結果が違う可能性 | 共通Stage 1から新規学習／run03継続 | 過去の増量と継続学習の結果を踏まえた対照 |
| 終了改善が正答率改善に直結しなかった | F11/F10をそろえた条件で比較し、採用主指標を正解率にする | Cの実測と提出結果に基づく判断 |
| 固定自己生成ペアでは改善が明確でなかった | 現在のモデルで生成し直すオンライン正誤報酬学習 | 10/15からのオンライン学習候補を具体化。ただし現在の目的関数は下記のとおり独自構成 |
| 1回では不正解でも複数生成で解けるか不明 | greedy／sampled pass@1／pass@8を診断 | 学習可能な正誤信号の有無を確認。提出時のbest-of-8選択ではない |

オンライン方式の背景には、10/15に調査した[DeepSeekMath](https://arxiv.org/html/2402.03300v3)、[Understanding R1-Zero-Like Training／Dr. GRPO](https://arxiv.org/html/2503.20783v2)、[REINFORCE／RLOOの研究](https://arxiv.org/html/2402.14740v2)がある。ただし**現在の実装はグループ平均・標準偏差で正規化した報酬によるon-policy REINFORCE、1 rolloutにつき1更新、KLなし**であり、GRPOのclipped目的関数、Dr. GRPO、leave-one-out baselineのRLOOをそのまま実装したものではない。10/20に新しい論文を選定してこの式を決めたという個別の調査記録はない。

### `_fix7`相当の改善をモデルの推論で実現するための次の方針

`/Users/cls-lab/Desktop/t4_20261014_run04_prmfull12k_calc_fix7.json`は、ユーザー申告では生成後に明らかな誤答を修正した版。モデルの未編集出力や追加学習済みモデルの成績とは区別する。`_fix7`自体のスコアは未確認で、上表には含めない。修正済みの評価答案をそのまま学習させたり、推論時に渡して復唱させたりすることを、今回の改善方法にはしない。

1. **比較の基準を固定する。** 既知の最高スコアのrun03を基準に、run04・run06を既存の固定devで比較する。正答率だけでなく、回答抽出失敗・長さ打切り・生成長を確認し、run06の低下が計算能力、解答形式、生成長のどこに現れるかを調べる。固定devでのrun02/run03比較は既存記録上未実施であり、今回も新たな評価は実行していない。
2. **修正内容は弱点の分類に使う。** 元の保存済み出力と`_fix7`の差分7件を照合し、回答中の演算を独立に検算した。run06にも7件すべてで計算誤りが残っていた。詳細は[回答比較](research/20261015_run03_run04_run06_output_audit.md)を参照。改善の成否は、別の学習外問題でも同種の誤りが減るかで確認する。
3. **追加学習の変更を一つずつ検証する。** 同じ出発モデル・同じ学習率・同じ更新数で、まず「同件数の固定seed抽出」と「演算記号スコア上位」の比較、または同一教材での「全非padding loss」と「回答＋EOSのみ」の比較を行う。run06の結果だけで、特定の選別法やlossを採用し続けない。実行する候補は基準評価の結果を見て決める。
4. **独立した教材で改善し、新しい出力を保存する。** 使用可能な教材の範囲で弱点に対応し、固定devを学習から除外したまま検証する。採用モデルで全件を再推論し、回答本文を編集せず保存する。モデル重み・教材・コードのハッシュ、推論設定、実行ログ、生の出力を残し、提出用JSONの回答との一致を確認できるようにする。

## エラーや中断が起きた場合

- 学習中の OOM は、他の GPU セッションを終了したうえで発生セルとライブラリの版を確認する。初回コピーは batch 1 に設定済み。追加で系列長を減らす場合は別実験として識別する。

- 学習条件やモデルを変える場合は、両ノートブックの RUN_ID と Stage 1 / 2 の保存先名を新しく揃える。異なるモデルや推論設定の途中結果を混ぜない。
